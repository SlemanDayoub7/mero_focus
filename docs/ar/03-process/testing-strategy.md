# استراتيجية الاختبار

كل ميزة (`features/<feature>/`) لها مجلد اختبار مطابق (`test/features/<feature>/`) يتبع نفس تقسيم الطبقات.

## مستويات الاختبار

| المستوى | ما يغطيه | الأدوات |
|---|---|---|
| **Unit Tests** | طبقة Domain بالكامل: usecases، منطق حسابات الإحصائيات (aggregation)، منطق تكرار العادات. الأولوية القصوى — الهدف تغطية قريبة من 100% هنا تحديدًا | `flutter_test` + `mocktail` |
| **Repository Tests** | تعامل الـ repository مع datasource المحلي (Drift)، مع mocking للـ datasource | `mocktail` |
| **Widget Tests** | شاشة المؤقت، شاشات الإحصائيات والفلاتر، شاشة إدارة العادات | `flutter_test` |
| **Integration Tests** | سيناريوهات كاملة: ابدأ جلسة → أكملها → تحقق تسجيلها بقاعدة البيانات → تحقق ظهورها صحيحة بالإحصائيات | `integration_test` |
| **Golden Tests** (اختياري، تُضاف تدريجيًا) | ثبات شكل الثيمات/الخلفيات بصريًا بين التحديثات | `golden_toolkit` |

## تعريف "خلص" (Definition of Done) لكل ميزة

ميزة لا تُعتبر منتهية إلا إذا توفر:
1. الكود الوظيفي كاملًا.
2. اختبارات Unit للـ usecases الجديدة على الأقل.
3. تحديث التوثيق ذو الصلة (ADR جديد إذا تغيّر قرار معماري، أو تحديث `data-model.md` إذا تغيّر الـ schema).

هذه القاعدة تُطبَّق من أول ميزة، حتى في العمل الفردي، لتصبح عادة ثابتة قبل انضمام أي متعاون لاحقًا.
