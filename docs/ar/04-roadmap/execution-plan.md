# خطة العمل (Execution Plan) — تنفيذ بمساعدة أدوات AI

## مبدأ الخطة

هذه الخطة مبنية على **جلسات عمل مركَّزة** وليس تواريخ تقويمية ثابتة، لأن سرعة الإنجاز الفعلية تعتمد على عدد ساعاتك المتاحة يوميًا، وهذا متغيّر لا نعرفه مسبقًا. كل "جلسة" هنا تعني فترة عمل مركّزة واحدة (نصف يوم تقريبًا)، سواء استُهلكت دفعة واحدة أو موزّعة.

**الافتراض الأساسي:** بما أن الآركتكتشر والمعايير (Clean Architecture، SOLID، صفر hard-coding، DI لكل feature) مثبّتة ومكتوبة بالكامل مسبقًا (هذا التوثيق نفسه)، فإن أي أداة AI تستخدمها (Claude Code، OpenCode، نسخة المتصفح، أو أي نموذج آخر) تملك سياقًا واضحًا وثابتًا تلتزم به، بدل أن تُعيد اختراع القرارات المعمارية بكل مرة — وهذا بالضبط ما يجعل إضافة أي feature لاحقة أسرع تصاعديًا، لا بنفس السرعة الثابتة.

## توزيع الأدوات حسب نوع المهمة (توصية عملية)

| نوع المهمة | الأداة الأنسب | السبب |
|---|---|---|
| بناء هيكل مشروع كامل، تعديل عدة ملفات مترابطة دفعة واحدة (مثل إنشاء feature كامل بطبقاته الثلاث) | أداة Agentic تعمل مباشرة على الملفات (Claude Code أو OpenCode) | تنفذ التعديلات فعليًا بدل نسخ/لصق يدوي، وتقرأ الكود الموجود فعليًا قبل التعديل |
| نقاش قرار معماري جديد، مراجعة ADR، حل مشكلة تصميم غامضة | نسخة محادثة (متصفح) مع سياق هذا التوثيق كامل | تفكير أعمق وحوار تكراري قبل الالتزام بكود فعلي |
| كود boilerplate متكرر النمط (مثل كتابة اختبارات Unit لعدة usecases بنفس الشكل) | أي نموذج سريع/اقتصادي متوفر لديك | لا يحتاج تفكيرًا معماريًا عميقًا، فقط اتباع نمط ثابت موضح بمثال واحد |
| مراجعة أمان/جودة كود قبل الدمج بـ main | نموذج قوي بالتحليل (مراجعة أخيرة قبل أي PR) | خطوة فحص أخيرة تستحق أعلى جودة متاحة |

**قاعدة عملية مهمة بكل الحالات:** أعطِ أي أداة AI تستخدمها ملف الـ ADR أو المعيار ذو الصلة مباشرة كسياق (مثلًا `coding-conventions.md` قبل أي طلب كتابة widget)، بدل الاعتماد على تذكّرها من محادثة سابقة — هذا يقلل كثيرًا من "الانحراف" عن المعايير المتفق عليها مع تراكم الجلسات.

## مراحل التنفيذ المقدَّرة

| المرحلة | المحتوى | تقدير (جلسات عمل) |
|---|---|---|
| 0 | تأسيس المشروع (`build-order.md` — المرحلة 0) | 1 جلسة |
| 1 | الأساس التقني: Drift كامل، الثيم، التعريب، Responsive، Routing (`AppRouter`) | 2–3 جلسات |
| 2 | Feature أول: `settings` كاملة (domain/data/presentation + اختبارات) — يُثبِّت القالب لكل ما بعدها | 1–2 جلسة |
| 3 | `pomodoro_timer` (المؤقت + منطق الجولات + Foreground Service حسب ADR-0009) | 3–4 جلسات (الأعقد تقنيًا بسبب الخدمة الخلفية) |
| 4 | `habit_tracking` | 1–2 جلسة |
| 5 | `statistics` (كل مستويات التجميع الزمني + الواجهات) | 2–3 جلسات |
| 6 | `app_lock` (الصلاحيات + شاشة الحجب) | 2 جلسة |
| 7 | `background_overlay` + ربطه الفعلي بـ Foreground Service من المرحلة 3 | 1–2 جلسة |
| 8 | `pdf_export` + ميزة النسخ الاحتياطي (Backup/Restore) | 1–2 جلسة |
| 9 | الهوية البصرية النهائية (أيقونة، Splash) + مراجعة شاملة لصفر hard-coding | 1 جلسة |
| 10 | قائمة فحص ما قبل النشر (`pre-launch-checklist.md`) بالكامل + اختبار على أجهزة حقيقية متعددة | 2–3 جلسات (تعتمد على عدد المشاكل المكتشفة فعليًا) |

**الإجمالي التقريبي: ~17–25 جلسة عمل مركّزة** للوصول لنسخة MVP جاهزة فعليًا للنشر (وليس فقط "تعمل على جهازك"). هذا رقم تقديري وليس التزامًا صارمًا — المرحلتان 3 و10 الأكثر عرضة للتمدد لأنهما تحتويان تعقيدًا تقنيًا حقيقيًا (خدمة الخلفية) أو اكتشافات غير متوقعة (اختبار أجهزة حقيقية).

## معيار تتبع التقدّم

استخدم نفس "تعريف خلص" الموثق في `testing-strategy.md` كخط فاصل بين المراحل: لا تنتقل لمرحلة تالية قبل أن تكون الحالية مبنية + مُختبرة + ناجحة على CI. هذا يمنع تراكم "دين تقني" صامت يصعب اكتشافه لاحقًا وسط تسارع الإنجاز بمساعدة AI.
