# ADR-0005: تأجيل نظام "المودات" (الجيمفكيشن) مع ضمان جاهزية البيانات له لاحقًا

**الحالة:** مقبول

## السياق
الفكرة الأصلية للمشروع تضمنت نظام "مودات" بصرية متعددة وقابلة للتبديل (تنانين، طيور، قطط...) تتطور مع تقدّم المستخدم، على طبقتين: تطور يومي (ضمن الجلسة) وتطور تراكمي طويل المدى. تم لاحقًا تأجيل بناء هذه الميزة فعليًا عن النسخة الأولى لصالح نطاق أبسط وأخف يشبه وظائف Focus To-Do الأساسية، مع الإبقاء على الباب مفتوحًا لإضافتها لاحقًا **دون فقدان بيانات المستخدمين الحاليين ودون عملية migration خطيرة**.

## القرار
1. لا تُبنى ميزة `mode_system` فعليًا في الـ MVP (لا UI، لا تخزين حالة مود).
2. **لا تُخزَّن أبدًا** أي بيانة من نوع "مستوى" أو "مرحلة تطور" كحقل مستقل في قاعدة البيانات.
3. جداول البيانات الأساسية (`focus_sessions`, `habit_logs`) تبقى **خامة بالكامل (raw facts)**: تواريخ، مدد، حالات إكمال — بدون أي إشارة لمود أو مستوى.
4. أي نظام مودات يُضاف مستقبلًا يحسب المستوى/التطور **ديناميكيًا (derived)** من البيانات الخام الموجودة أصلًا، وقت العرض، عبر دالة محض (pure function) تقرأ من `focus_sessions` و`habit_logs`.

## الأسباب
- يجعل النسخة الأولى أخف وأسرع إنجازًا (لا جداول أو منطق مودات زائد).
- يُلغي الحاجة لأي عملية migration بيانات لاحقًا: المستخدم القديم الذي راكم مئات ساعات التركيز سيظهر تلقائيًا بمستوى متقدم فور تفعيل نظام المودات مستقبلًا، لأن الحساب مبني على سجل استخدامه الحقيقي، لا على بيانة مود كانت يجب ترحيلها.
- يفصل تمامًا منطق "الحقائق" (ماذا فعل المستخدم فعليًا) عن منطق "العرض التحفيزي" (كيف نعرض ذلك بصريًا)، وهذا يسمح بتعدد طبقات عرض تحفيزية مختلفة فوق نفس البيانات مستقبلًا دون أي تعارض.

## النتائج المترتبة
- مجلد `features/mode_system/` يبقى موجودًا في هيكل الآركتكتشر (ADR-0002) كموضع محجوز، لكن فارغًا من التنفيذ الفعلي في الـ MVP.
- أي عمل مستقبلي بهذا الاتجاه يبدأ بكتابة ADR جديد يوثّق تصميم دوال الحساب (`calculateLevel`, `calculateEvolutionStage`, إلخ) دون الحاجة لتعديل جداول `focus_sessions` أو `habit_logs` الحالية.
